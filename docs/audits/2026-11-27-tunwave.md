## Findings

1. **TLS bad record MAC remains unexplained.** Prior checkpoint 03 attributed the failure to an old long-lived agy process. DIAG-PLAN-r2 explicitly withdrew that conclusion: fresh agy 1.5.17 clients on a new node subsequently reported 34 and 12 MAC errors. The later quiet window included mostly idle client traffic. A sentinel completed 23 byte-verified 120-second streams, but it did not overlap a captured failure wave. No decisive owner packet capture was present in the inspected diagnosis evidence. Client, Darwin TUN path, outbound/node and load hypotheses remain open.
2. **A separate NAT defect is reproducible.** The preserved sing-tun v0.8.3 TCPNat source allocates ports from a wrapping uint16 counter without checking live occupancy and keys its forward map by source alone. Old source mappings can outlive overwritten reverse entries. Historical deterministic tests reproduced collision/leak behavior; historical Linux lab reports showed post-wrap dial stalls for system/mixed and 40/40 successful streams for gvisor. None established byte corruption or a causal link to MAC. This audit inspected source and receipts; it did not rerun a TUN lab.
3. **Source and runtime have diverged.** Control main is 60861f9. The locally recorded origin/main is 37e6727, 91 commits ahead. Prior STOP-d614 handoff independently names that source head. Accepted upstream source includes TUN-stack configuration/helper schema support, reconnect preflight/rollback, identity-bound process handling, fail-closed PF support, maintenance readback and unknown-process-state fixes. The installed artifact/helper versions and R6 installation outcome were not verified. No automatic merge, install or runtime adoption was performed.
4. **The old control checkout retains known risky behavior.** Its orphan-sidecar cleanup may signal a name/config match without start identity. The later upstream implementation refuses such discoveries. Its uncommitted route retry checks a deadline between unbounded route subprocess calls, so the advertised eight-second window is not a hard operation deadline. These are source findings, not a claim that the live helper ran either path.
